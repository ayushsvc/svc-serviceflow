# SVC ServiceFlow Deployment Guide

This guide describes the production topology in the repository's root `render.yaml`, deployment steps, and hosting trade-offs for this project.

## Project deployment architecture

| Component | Render resource | Purpose |
|---|---|---|
| Frontend | Public Next.js web service | UI, login, and same-origin `/api/v1/*` proxy to the private API |
| API | Private FastAPI Docker service | Authentication, tickets, uploads, and business APIs |
| Background work | Celery worker | Asynchronous application jobs |
| Scheduled work | Celery beat | Runs SLA and recurring-ticket jobs every 60 seconds |
| Relational data | Managed PostgreSQL | Users, tickets, configuration, audit, and other application records |
| Queue/cache | Render Key Value (Redis-compatible) | Celery broker/backend, invitation state, rate limits, and token revocation |
| Uploaded files | API persistent disk at `/app/data/documents` | Ticket attachment data |

The browser sends API calls to the web service's `/api/v1/*` path. Next.js rewrites those requests to `API_INTERNAL_HOSTPORT` over Render's private network, so the API does not need a public URL. The frontend Docker build receives this internal API address through the Blueprint. Locally, Docker Compose continues to use `api:8000`.

The API runs database migrations in `preDeployCommand`, then runs the production seed and starts Uvicorn. The production seed prepares entity defaults and creates the configured initial administrator; it does not create demo users. Keep `DEBUG=false` and do not enable demo seeding in production.

## Set up the Blueprint

1. Push the intended release branch to GitHub and create or connect a Blueprint using the repository's root `render.yaml`. The Blueprint currently has `autoDeploy: false`, so a push alone does not release the application.
2. Review the Blueprint services, region, plans, and resulting monthly estimate in Render before creating paid resources. Keep the web, API, worker, beat, database, and Key Value resources in the same region.
3. During Blueprint setup, provide the values marked `sync: false`:

   | Variable | Set it to |
   |---|---|
   | `CORS_ORIGINS` | Exact public web origin, e.g. `https://your-service.onrender.com`; no trailing path or wildcard |
   | `APP_BASE_URL` | Exact public web URL; invitation emails link back to this site |
   | `SMTP_USERNAME`, `SMTP_PASSWORD` | Credentials for the selected SMTP provider, e.g. a verified Brevo SMTP account |
   | `MAIL_FROM` | Sender address authorized by that provider and your verified domain |
   | `SEED_ADMIN_EMAIL`, `SEED_ADMIN_NAME`, `SEED_ADMIN_PASSWORD` | Initial administrator identity. Use a unique password of at least 16 characters and no more than 72 UTF-8 bytes |
   | `INVITE_ALLOWED_EMAIL_DOMAINS` | Optional comma-separated allow-list, e.g. `example.com,partner.org`; leave blank for no domain restriction |

   `JWT_SECRET` is generated by Render. Database and Redis connection strings are wired from the managed resources. Invitation and acceptance limits default to 30 invite/resend attempts per admin per hour and 10 acceptance attempts per IP and token per 15 minutes.
4. Configure SPF and DKIM for the mail sender domain with your DNS provider before relying on invitation or ticket email.
5. Deploy the Blueprint and wait for both the public web service and private API health checks to pass.
6. Sign in with the initial administrator, verify the People → Users page, and invite a test account. Confirm the recipient receives the message and that its link opens the deployed site.

The production seed initializes entity defaults and creates only the configured first administrator. It does not create the local demo technician/requester accounts, does not overwrite existing passwords, and does not auto-assign invited technicians to teams. Subsequent technicians and requesters should be invited through the application.

## Releasing updates

1. Review and test the changes locally; do not put production secrets in the repository.
2. Push the approved commit to the branch connected to the Blueprint.
3. In Render, manually deploy the intended latest commit because automatic deploy is disabled.
4. Check the API and web health checks, service logs, and the migration output before testing sign-in, ticket creation, upload/download, invitation email, and scheduled jobs.
5. If the deployment fails, inspect the service and pre-deploy logs. Roll back to a known-good application commit or image as appropriate. Database migrations may not be reversible, so review any migration before deployment and take a database backup before a risky schema change.

The Render API health check is `/health`; the web health check is `/`. The API migration runs as a pre-deploy command. No migration is introduced by this deployment guide.

## Hosting recommendation and estimated cost

**Best fit for this project: Render.** The current repository already defines the Next.js app, private FastAPI service, Celery worker and scheduler, managed PostgreSQL, Redis-compatible Key Value, and persistent upload disk as one Blueprint. Render provides the least operational work for this design: deployments, private service networking, health checks, environment groups, and managed data services are handled in one platform.

**Lowest likely infrastructure bill: one self-managed VPS.** For example, Hetzner currently advertises Cloud plans starting at €5.99/month excluding VAT, but this is not a like-for-like managed-platform comparison. You would operate Docker, TLS/reverse proxy, OS and container updates, PostgreSQL and Redis backups, monitoring, firewall rules, and disaster recovery yourself. Confirm the current plan's capacity and availability in your target location before choosing it; a single VPS is also a single failure domain.

| Option | Planning cost | Operational effort | Fit for ServiceFlow |
|---|---:|---|---|
| Render Blueprint in this repository | Approximately **$46.50/month** at current smallest listed paid plans: four Starter compute services ($28), Basic-256mb Postgres ($6), Starter Key Value ($10), and 10 GB API disk ($2.50) | Low | Recommended for a first production deployment; managed services, but each resource is billed separately |
| Hetzner Cloud VPS | Advertised entry from **€5.99/month excl. VAT**; backups, email, domain, and any extra resources are additional | High | Cheapest if you can operate and secure a Linux server yourself; all services share one host unless you add more infrastructure |
| DigitalOcean Droplet | Basic 4 GiB Droplet is listed at **$24/month**; managed PostgreSQL is separate and starts around **$15.15/month** | Medium to high | Straightforward VPS alternative, but a managed-data setup costs more than the Droplet price alone |
| Railway Hobby | **$5/month plan fee includes $5 of usage**, then resource and egress usage are billed | Low to medium | Easy to try, but the always-on web/API/worker/beat plus data services can exceed the included usage; estimate in its calculator first |

Render's estimate excludes usage beyond included allowances, database storage beyond the plan, bandwidth/egress, taxes, optional domain/email-provider charges, and any plan changes. Treat these values as a comparison baseline, not a quote; prices and plan availability can change. Check the provider pricing pages before provisioning.

### Cost controls and production trade-offs

- For a demo, temporary free resources can reduce cost, but sleeping/limited resources are not a reliable production service and may not provide durable storage.
- Do not remove Redis: this application uses it for Celery and authentication/invitation controls.
- Do not remove the persistent API disk unless uploads have first been moved to durable shared object storage.
- Keep the API at one instance while local disk stores uploads; Render disks are not shared across instances.
- A single VPS may be cheapest but puts the application and its data services on one machine. Maintain off-host database and upload backups and test restoration before using it with real users.
- If cost is the deciding constraint but managed hosting is preferred, compare actual monthly resource estimates on Render and Railway with the expected always-on memory, CPU, storage, and egress. A plan's minimum fee is not necessarily the total bill.

## Known limitations

The notification bell is a derived activity feed, not stored notification rows. Read state is stored per browser, the feed polls every 60 seconds, and it does not include assignment or ticket-creation events. A stored notifications table is planned.

## Important storage note

Render's disk is attached only to the API service. Ticket upload and download requests go through that API, so those files remain on the persistent disk. Do not scale the API above one instance while using local disk storage: a Render disk is not shared across instances. For horizontal API scaling, migrate uploads to shared object storage first.
